# 校内赛小车通信与手柄前处理开发计划书

## 1. 本轮重构原因与边界

裁判系统现在可以直接通过 ESP32-S3 的 UART1 通信。因此 ESP32 不再只从主控获得裁判汇总状态，而是同时承担手柄前处理、裁判串口适配、主控执行事件交换和 Wi-Fi 比赛通信。

本文件是下一版协议与固件的设计基线，先冻结职责和接口，再实现。当前固件中的 UART `ping/pong`、UART0/1 原始 Xbox 数据镜像和比赛假数据，均视为临时自检代码，不能作为正式业务行为。

ESP32 不负责电机闭环、底盘运动学、射击执行或裁判判定；主控 STM32 负责实际控制和执行。L431PM 维护 HP、存活状态、比赛开始/结束状态与比赛射击许可，并接入枪管热量和装甲板受击输入。比赛射击许可与底盘通断电独立。

## 2. 已冻结的硬件与通信拓扑

```text
Xbox 手柄
   │ BLE HID
   ▼
ESP32-S3
   ├── UART0，GPIO43 TX / GPIO44 RX，115200 ──────── 主控 STM32
   ├── UART1，GPIO17 TX / GPIO18 RX，115200 ──────── L431PM USART2
   └── Wi-Fi UDP ─────────────────────────────────── 比赛服务器
```

| 链路 | 正式职责 | 禁止的正式用途 |
|---|---|---|
| UART0：ESP32 → 主控 | 仅发送精简手柄控制 | 裁判状态回传、执行事件回传、服务器命令转发、原始 Xbox HID |
| UART1：ESP32 ↔ L431PM USART2 | 接收/发送 L431 裁判与电源协议；解析本车比赛状态 | Xbox 镜像、常规调试输出 |
| Wi-Fi UDP | 状态、比赛事件、服务器下行与 ACK | 电机实时闭环或手柄控制主路径 |
| USB Serial/JTAG | 烧录和诊断日志 | 正式业务数据 |

UART0/UART1 均按 `115200, 8N1, 无硬件流控` 设计。UART1 的 L431 侧使用 USART2：PA2 为 TX、PA3 为 RX；接线交叉且共地。L431 当前已初始化 USART2，但其现有 `bsp_uart`、中断和 ASCII 协议任务仍只绑定 LPUART1（PC0/PC1），所以 **USART2 驱动尚未真正接入业务，必须先补齐**。

## 3. 数据权威与流向

| 数据 | 权威来源 | ESP32 动作 | 服务器动作 |
|---|---|---|---|
| 摇杆、扳机、按键 | Xbox 手柄 | BLE 解码、死区/缩放，经 UART0 发主控 | 不上传原始控制数据 |
| HP、热量、功率、存活/死亡、射击许可 | L431 UART1 | 解析为最新状态；补入 ESP32 保存的机器人 ID 后，以完整 10 Hz 状态上报 | 保存/显示状态 |
| 攻击、受击、死亡、复活 | L431 UART1 | 生成独立 UDP 事件 | 记录比赛事件并 ACK 关键事件 |
| 比赛开始/结束、设置 HP、黄牌处罚 | 服务器 | 经 UART1 请求 L431 执行，等 L431 回执再 UDP ACK | 可靠重传直至确认/失败 |
| 机器人 ID、手柄 MAC 分配 | 服务器 | ESP32 保存；不转发主控或 L431 | 可靠下行，等待 ESP32 ACK |

同一事件必须只有一个最终上报入口，禁止裁判系统和主控同时上报导致重复。

## 4. 正式 UART 协议框架

正式 UART 帧均为固定长度、二进制、小端序、2 字节帧头、序号或事务号、CRC-8/ATM。接收端使用环形缓冲和帧头重同步；CRC 或长度错误只丢弃当前候选帧。

### 4.1 ESP32 → 主控：控制状态

保留 14 字节控制帧，100 Hz：

```c
typedef struct __attribute__((packed)) {
    uint8_t magic0;          // 0xC3
    uint8_t magic1;          // 0x3C
    uint8_t sequence;        // 0..255
    uint8_t flags;           // bit0: BLE 已连接；bit1: 已收到有效 HID
    int8_t  left_x, left_y, right_x, right_y;
    uint8_t left_trigger, right_trigger;
    uint8_t dpad, buttons_1, buttons_2;
    uint8_t crc8;
} controller_state_frame_t;
```

摇杆先按原始 Xbox 方向发送，死区暂定 `±8 / 127`。超过 `100 ms` 未收到有效 HID 时，ESP32 发送零控制量并清除有效标志；主控超过 `150 ms` 未收到有效控制帧时停止运动和射击。

### 4.2 UART1：L431 裁判/电源适配层

L431 USART2 已用于该链路，具备中断收发队列和独立二进制协议：L431 主动发 10 Hz 状态与异步比赛事件；ESP32 只负责解析、上报 Wi-Fi，并把服务器偶发控制指令转给 L431。L431 自身维护 HP；装甲板受击上报后扣血，服务器下发设置 HP 时更新 HP。LPUART1 保留 `\r\n` 结尾 ASCII 电源调试协议，并向主控输出 `FIRE=ON/OFF` 比赛许可；它不与 USART2 复用。现有 `app_referee_can` 已保存枪管的 `heat_level`、有效射击计数和装甲板命中计数。

UART1 的 10 Hz 状态帧使用 11 字节固定二进制帧。机器人 ID 由服务器分配并由 ESP32 NVS 保存，L431 不重复传输；其余所有正式状态字段均由 L431 提供：

```c
typedef struct __attribute__((packed)) {
    uint8_t  magic0;        // 0xA5
    uint8_t  magic1;        // 0x5A
    uint8_t  sequence;      // 0..255
    uint8_t  flags;         // bit0: alive；bit1: shoot_enabled；bit2: power_on
    uint16_t hp;            // 小端
    uint16_t heat;          // 小端，裁判热量原始整数单位
    uint16_t power;         // 小端，100 ms 平均功率，整数 W
    uint8_t  crc8;          // CRC-8/ATM，覆盖 magic0 至 power
} l431_status_frame_t;     // 11 字节
```

ESP32 将上述实时字段与已分配的 `robot_id` 拼成完整的 V2 UDP 状态帧：

```c
typedef struct __attribute__((packed)) {
    uint16_t magic;         // 0x5254
    uint8_t  version;       // 2
    uint8_t  frame_type;    // 状态帧
    uint8_t  robot_id;
    uint16_t hp;
    uint16_t heat;
    uint16_t power;
    uint8_t  alive;
    uint8_t  shoot_enabled;
    uint8_t  power_on;
} robot_status_v2_frame_t; // 14 字节
```

计划内部接口：

```c
void referee_update_status(uint16_t hp, uint16_t heat, uint16_t power,
                           bool alive, bool shoot_enabled);
void referee_publish_event(referee_event_t event);
```

UART0 不回传裁判状态给主控；主控仅接收手柄控制。

L431 的六种异步事件均为 4 字节独立帧，ESP32 只按事件含义上报 UDP：

| 事件 | UART1 帧 |
|---|---|
| 攻击 | `B1 1B | sequence | crc8` |
| 受击 | `B2 2B | sequence | crc8` |
| 死亡 | `B3 3B | sequence | crc8` |
| 复活 | `B4 4B | sequence | crc8` |
| 允许射击 | `B5 5B | sequence | crc8` |
| 禁止射击 | `B6 6B | sequence | crc8` |

死亡/复活事件优先进入可靠 UDP 队列。ESP32 同时观察 10 Hz `alive` 状态：若 UART1 的死亡/复活事件遗漏，状态变化会补发同一类可靠事件；实现时以最近一次已上报的 alive 状态去重，避免同一次变化重复上报。

### 4.3 UART1：服务器命令转发与 L431 回执（预留）

服务器可靠下行中的比赛开始、比赛结束、设置 HP 和黄牌处罚将经 UART1 交给 L431。L431 在自身业务状态机中执行；比赛开始由 L431 设置 `HP=300、alive=1` 并清除本场黄牌和判负状态。ESP32 在 `200 ms` 内等待 L431 回执，成功才向服务器回复成功 ACK；L431 回执固定映射为：`0=成功`、`1=不允许`、`2=失败`。

| ESP32 → L431 命令 | 帧 | 长度 | L431 → ESP32 回执 |
|---|---|---:|---|
| 比赛开始 | `C1 1C | transaction_id[4] | crc8` | 7 | `D1 1D | transaction_id[4] | result | crc8` |
| 比赛结束 | `C2 2C | transaction_id[4] | crc8` | 7 | `D2 2D | transaction_id[4] | result | crc8` |
| 设置 HP | `C3 3C | transaction_id[4] | hp[2] | crc8` | 9 | `D3 3D | transaction_id[4] | result | crc8` |
| 黄牌处罚 | `C4 4C | transaction_id[4] | crc8` | 7 | `D4 4D | transaction_id[4] | result | crc8` |
| 强制断电 | `C5 5C | transaction_id[4] | crc8` | 7 | `D5 5D | transaction_id[4] | result | crc8` |
| 请求通电 | `C6 6C | transaction_id[4] | crc8` | 7 | `D6 6D | transaction_id[4] | result | crc8` |

L431 以 `transaction_id` 去重：同一事务重复到达时不重复执行，只回相同结果。

机器人 ID、手柄 MAC 分配只由 ESP32 保存，不发送主控或 L431。

## 5. Wi-Fi UDP 协议与可靠性

README 是 UDP 结构的唯一发布依据。正式 ESP32 固件仅发送 V2；服务器若需要兼容旧测试固件，可保留 V1 解析，但 ESP32 不重复发送 V1。

- V1：历史测试协议；ESP32 正式版不发送。
- V2：完整 10 Hz 状态帧为 14 字节，字段为机器人 ID、HP、热量、平均功率、存活、射击许可和底盘供电状态；攻击、受击不带事务号且不 ACK。死亡、复活和改变 ESP32/L431 状态的下行命令，在各自独立帧末尾追加 `uint32_t transaction_id`。
- ACK：`magic | version=2 | type=0xF0 | acked_frame_type | transaction_id[4] | result`，共 10 字节；它只是传输确认，不携带业务命令。
- 请求状态不 ACK；仅在 L431 链路有效时目标车立即回当前状态。链路断开时不回复缓存状态，服务器通过既有链路断开事件判断原因。
- 广播比赛开始/结束时，各车收到后立即向服务器回 ACK；服务器必须允许多个 ACK 在短时间内到达，并以同一事务号重试。重复事务只重发原 ACK，不重复转发 L431。
- ESP32 只接受配置服务器 IP 的下行包；ACK 回到该数据报的源 IP/端口。
- V2 增加两个独立、不可靠事件：`frame_type=0x08` 为 L431 链路断开、`0x09` 为链路恢复。连续 `300 ms` 没有合法 L431 状态帧时触发断开；随后连续 3 帧合法状态触发恢复，每次状态变化只上报一次。

ESP32 上行可靠流程：持久化待确认事务 → 首次发送 → 等 `100 ms` → 最多重发两次 → 收到匹配 ACK 后删除记录。失败不可阻塞 UART0、UART1、BLE 或 10 Hz 状态发送。

## 6. NVS 持久化与重启安全

- 仅保存未 ACK 的上行死亡/复活事务，最多 4 条；重启后继续重发。
- 保存最近已执行的下行事务号和结果；重复下行只重发 ACK，绝不重复设置 HP、开始或结束比赛。
- 保存服务器分配的机器人 ID 和手柄 MAC。
- 不保存完整 UDP 历史、Xbox 历史、裁判原始字节、HP、alive 或射击许可；这些由 UART1 重新建立。
- ESP32 不擅自连接未知手柄：没有服务器分配的 MAC 时保持 BLE 不连接；断线后只在一个待冻结的短时间窗口内重连同一已分配地址。
- 收到新的服务器分配 MAC 后，ESP32 立即断开旧手柄并只扫描该新地址；断线后仅重连最近一次已分配地址 `30 s`，超时停止扫描。
- 未分配机器人 ID 或手柄 MAC 时，ESP32 不发送正式 UDP 状态，避免 `robot_id=0` 被服务器误认为有效小车。

## 7. 测试模式与本地 Python CLI

正式比赛只使用 `CONFIG_ROBOT_WIFI_SSID` 配置的主 Wi-Fi。测试模式 `CONFIG_ROBOT_TEST_MODE=y` 时保留主 Wi-Fi 优先级不变：上电立即连接主 Wi-Fi；若上电满 `10 s` 仍未获得 IP，ESP32 才切换尝试备用测试 Wi-Fi `evil rats crazily squeak`。备用密码由私有配置保存为 `66666666`，不得在正式模式启用，也不得替换主 Wi-Fi 的比赛配置。

测试用服务器为本仓库的 Python CLI，而不是正式比赛服务器。CLI 监听 UDP、打印/记录 V2 完整状态与事件，并可手动发送分配 ID/MAC、开始、结束、设置 HP、请求状态等下行帧。它必须能观察 ACK、重传与裁判链路断开/恢复事件，但不承担正式服务器开发责任。

## 8. 任务与实时性

| 任务 | 规则 |
|---|---|
| NimBLE 回调 | 只复制最新 HID；禁止 UDP、NVS、阻塞 UART、大量日志 |
| 控制帧任务 | 100 Hz 向 UART0 发最新控制状态；绝不等 Wi-Fi 或裁判任务 |
| UART0 控制发送 | 单向 100 Hz 手柄控制；不接收正式业务数据 |
| UART1 接收/发送 | 高优先级解析 L431 状态、事件和回执；与 UART0 独立缓冲 |
| UDP 状态 | 10 Hz 发送最新裁判状态，不排队旧状态 |
| UDP 可靠事务 | 独立队列管理 ACK/重传/NVS，不阻塞控制与裁判解析 |
| NVS 工作 | 仅事务创建/完成时低频执行，不在 ISR 或 BLE 回调中运行 |

Wi-Fi 与 BLE 共享 2.4 GHz，但控制主路径是 UART0。验收时测试四车、服务器、四手柄同时运行下的 UDP、BLE、UART CRC、可靠事务完成率和裁判状态更新时间。

## 9. 分阶段实施

1. 获取并冻结 UART1 裁判协议、接线和电平；删除 UART1 `ping/pong` 与 Xbox 镜像的正式依赖。
2. 完成 UART0 单向控制帧和主控失联保护。
3. 在 L431PM 实现 USART2 中断、收发队列和协议任务，再实现 ESP32 UART1 适配层。
4. UDP 完整状态和事件均改由 L431 内部状态产生；ESP32 仅补入服务器分配的机器人 ID 并负责无线传输。
5. 在 ESP32 测试模式加入主 Wi-Fi 优先、10 秒后的备用 Wi-Fi 回退，并实现 Python 测试服务器 CLI。
6. 冻结 V2 每种独立帧长度，实施 ACK、重传、NVS 去重恢复和 UART1 的 L431 命令/回执。
7. 联调四车广播开始/结束、单播分配、设置 HP、断网重连、ESP32/L431 重启与重复包。
8. 关闭比赛假数据、备用 Wi-Fi 与临时原始串口输出，完成满载无线和整车安全测试。

## 10. 已冻结的比赛状态机

- L431 上电：`hp=0`、`alive=0`、比赛结束；ESP32 不发送正式 UDP，直到服务器已分配 ID/MAC 且 L431 链路有效。
- 服务器开局顺序：向每车发送 `比赛开始` 并等 ACK；L431 收到后自行设置 `HP=300`、进入存活状态，再由服务器视为开局成功。
- 装甲板一次有效受击：若当前存活，HP 减 `20` 并发受击事件；HP 变为 `0` 时立刻发死亡事件、启动 `5 s` 复活计时。
- 正常复活：5 秒计时完成后，L431 设置 `hp=300`、`alive=1` 并发复活事件。
- 服务器 `SET_HP` 是管理员覆盖：设为正数时若当前死亡立即复活并取消读条；设为 `0` 时立即死亡并启动 5 秒读条。
- 比赛开始由 L431 设置 `HP=300`、`alive=1`，清零黄牌并解除判负；比赛结束停止比赛业务。HP 归零后的 5 秒复活仅在比赛进行中且未判负时执行。
- 服务器每判定一次恶意高速撞击就发送一次黄牌处罚命令；L431 本场累计黄牌，第 1、2 次扣 50 HP，第 3 次直接判负且不再自动复活。
