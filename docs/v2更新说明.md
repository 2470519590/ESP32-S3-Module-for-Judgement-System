# V2 更新说明与迁移清单

V2 是校内赛 1v1 正式通信协议。它替代旧 ESP32 测试固件中的 V1 UDP 帧；**同一台正式 ESP32 只发送 V2，不并发发送 V1**。完整结构以 [README.md](../README.md) 为准。

## 1. 破坏性变化

| 项目 | V1 测试协议 | V2 正式协议 |
|---|---|---|
| 版本 | `version=1` | `version=2` |
| 队伍 | 每帧含 `team` | 1v1 移除队伍字段 |
| 状态帧 | 10 B：ID、队伍、HP、存活、射击许可 | 14 B：ID、HP、热量、平均功率、存活、射击许可、底盘供电 |
| 受击帧 | 8 B，携带受击后 HP | 5 B，仅表示受击；最新 HP 读状态帧 |
| 战斗状态 | 旧测试语义可能是逐发攻击 | `0x05` 进入战斗，连续 800 ms 无有效射击后以 `0x0B` 脱离战斗 |
| 身份分配 | ID、队伍、MAC | ESP32 Wi-Fi MAC 精确寻址的 ID、手柄 MAC 分配，且可靠 ACK |
| 下行目标 | ID + 队伍过滤 | 仅非零 `target_robot_id`，不支持比赛控制广播 |
| 可靠性 | 无 ACK、无事务号 | 死亡/复活和关键下行使用 `uint32_t transaction_id`、ACK、重传、去重 |

不能根据 V1 的长度推断 V2。服务器必须先读取 `magic/version/frame_type`，再严格检查该 V2 类型的固定长度。

## 2. V2 上行变化

### 状态帧

V2 状态帧长度为 14 字节：

```text
54 52 (little-endian magic 0x5254)
02 (version)
01 (status type)
robot_id
hp[2] heat[2] power[2]
alive
shoot_enabled
power_on
```

多字节字段小端序。`power` 为发送端提供的整数瓦特值；`heat` 为发送端提供的热量值。服务器只按字段位置和类型解析，不需要了解字段的设备内部来源。

### 事件

- 死亡 `0x02`、复活 `0x03`：9 字节，末尾含 `transaction_id[4]`，必须 ACK。
- 受击 `0x04`、进入战斗 `0x05`、允许/禁止射击 `0x06/0x07`、脱离战斗 `0x0B`：均 5 字节，不 ACK。
- L431 链路断开/恢复 `0x08/0x09`：均 5 字节，不 ACK。

服务器要以 `(robot_id, frame_type, transaction_id)` 去重死亡/复活；重复收到时仍回 ACK，业务层只处理一次。

### 设备注册

`0x0A DEVICE_ANNOUNCE` 为 25 字节，每 2 秒上报：

```text
54 52 02 0A robot_id esp32_wifi_mac[6] controller_ble_mac[6]
event_queue_drops[4] udp_send_failures[4]
```

服务器以 ESP32 Wi-Fi MAC 为设备主键，记录源 IP、当前机器人 ID、手柄 MAC 和两项诊断计数。新板 `robot_id=0`，先注册再按其 MAC 分配身份。

## 3. V2 下行变化

服务器建议使用绑定 `5005` 的同一个 UDP socket 接收 ESP32 上行并发送下行到 ESP32 的 `5006`。ESP32 的下行 ACK 会发回服务器下行包的源 IP/源端口；如果服务器从 `5005` 发出，下行 ACK 就会回到服务器 `5005`。

| 命令 | 类型 | 长度 | 可靠性 |
|---|---:|---:|---|
| 比赛开始 | `0x81` | 9 B | ACK |
| 比赛结束 | `0x82` | 9 B | ACK |
| 分配 ID/MAC | `0x83` | 21 B | 带目标 ESP32 Wi-Fi MAC；按设备注册帧源 IP 单播 |
| 请求状态 | `0x84` | 5 B | 不 ACK，收到的是额外状态帧 |
| 设置 HP | `0x85` | 11 B | ACK |
| 黄牌处罚 | `0x86` | 9 B | ACK |
| 强制断电 | `0x87` | 9 B | ACK |
| 请求通电 | `0x88` | 9 B | ACK |

可靠命令末尾有 `transaction_id[4]`。服务器第一次发送后等待 100 ms，未获 ACK 最多重发两次；重发必须保持相同事务号。ESP32 对重复命令不重复转发 L431，只回原 ACK。

ACK 类型 `0xF0`，10 字节：

```text
magic[2] | version=2 | type=F0 | acked_frame_type |
transaction_id[4] | result
```

`result=0` 成功，`1` 不允许，`2` 失败。

## 4. 服务器迁移顺序

1. 先让服务器同时识别旧 V1 与新 V2 上行包，日志必须标出版本。
2. 增加 V2 的 14 字节状态解析、9 字节死亡/复活去重和 ACK 回复。
3. 先接收 `0x0A` 并建立设备表；按 ESP32 Wi-Fi MAC 分配 ID/手柄 MAC，再发送比赛开始并确认（设备自行设置 `HP=300`）；所有比赛控制逐车单播。支持强制断电和请求通电并等待 ACK。
4. 将每台升级到 V2 的 ESP32 切为仅发送 V2；确认该车不再发送 V1 后再移除其 V1 处理。
5. 所有车辆升级完成后，服务器可移除 V1 业务入口。

## 5. 固件协同变更

- ESP32：移除 `team`、接入 L431 UART1 状态和事件、实现 V2 UDP/ACK/NVS/下行；测试模式的备用 Wi-Fi 与 Python CLI 已存在。
- L431PM：实现 USART2 独立驱动和本文档对应状态机，复用现有枪管/装甲板 CAN 监控字段。详见 [L431PM_对接任务提示词.md](L431PM_对接任务提示词.md)。
- 装甲板：不修改比赛帧；继续发已有自动 NodeID 下的 HIT CAN 事件。详见 [装甲板固件对接说明.md](装甲板固件对接说明.md)。

## 6. 当前测试阶段的特殊说明

当前 ESP32 测试固件使用“真实 L431PM 数据 + 测试 Wi-Fi”，`CONFIG_ROBOT_TEST_MODE=n` 时不会生成 V1 或 V2 假比赛数据。`host/test_server_cli.py` 保留 V1 解码能力只是为了读取历史日志；当前 ESP32 正常上报仅为 V2。

当前 CLI 用 `DEVICE_ANNOUNCE` 建立当前在线的 `robot_id ↔ ESP32 Wi-Fi MAC ↔ 当前 IP ↔ 手柄 MAC` 表；`devices` 查看该表，用户只需输入 `assign ROBOT_ID CONTROLLER_MAC`。CLI 自动选择唯一未分配设备，并把其 MAC 封装进分配帧校验；多台未分配设备同时在线时会拒绝猜测。CLI 不保存电脑本地设备表：重启后等待 ESP32 再次上报其 NVS 中保存的机器人 ID 和手柄 MAC，才允许发送命令。CLI 的黄牌命令只用于触发设备端本场黄牌处罚。
